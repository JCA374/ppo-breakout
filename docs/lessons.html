Part 1 · Lessons learned in this project

1. Measure before you optimise

The plan allowed for porting the hot loop to a compiled language if 10 M frames wouldn't fit in 12 hours. A one-minute timing run showed 288 agent steps per second: 2.4 hours. The simulator (envpool, C++) alone was 14× faster than the whole loop, and three quarters of each iteration is PyTorch's backward pass. There was nothing to port.

2. More threads can be slower

8 PyTorch threads ran at 225 steps/s, 4 threads at 288. The laptop has 4 physical cores; envpool's emulator threads and PyTorch's threads fight over them, and minibatches of 256 are too small to split 8 ways.

3. Test the resume before you need it

The 10-minute smoke test ran as two 5-minute halves, the second resuming from the checkpoint the first left behind. The resume carries the optimizer state, the iteration (so the learning-rate schedule continues), the RNG states and the MLflow run id (so the curves continue in the same MLflow run).

4. Same seed, same numbers

The main run reproduced the smoke test's numbers to the last digit for the iterations they share (for example iteration 80: KL 0.003878, clip fraction 0.140). envpool with a fixed seed and PyTorch on CPU are deterministic here, which makes a resume or a comparison of two settings much easier to trust.

5. MLflow 3 refuses its own file store

MLflow 3.x raises an error for a ./mlruns file store unless MLFLOW_ALLOW_FILE_STORE=true is set; it wants a database. The file store still works and is what this project uses; every script sets the variable.

6. Check the units of a borrowed budget

The plan said "10 M frames", taken from CleanRL's total_timesteps=10M. But CleanRL counts agent steps, and each step is 4 frames: its Breakout results are for 40 M frames, like the PPO paper's. The run's flat score at 1.4 M frames prompted the check. The fix cost nothing but a restart from the latest checkpoint with a longer learning-rate schedule; found at 10 M frames, it would have cost 3 hours.

7. "The score" depends on the evaluation protocol

At 15 M frames, the same model scored 185 on 20 games with the standard training wrappers (a lost life is an episode boundary, with a soft reset and automatic FIRE) and 139 on plain full games, where it has to relaunch the ball itself. Same model, same seeds, same scoring of the whole game; only what happens at a lost life differs. Since then every goal check runs both protocols and says which is which. And 10 games are noisy: on 10 games the same model averaged 86.5.
